# Second rating of the declared-only judgments — review package

The `docs/matching-v6-declared-only-analysis.md` study left one question open,
and named it as the highest-value next step: **its declared-only expectations
were rated by an AI assistant, not a human.** Every policy comparison in that
document turns on 34 observations, 14 of them flagged contested by that single
rater. This package exists to put a human second rater on those rows, blind, and
to compute what follows.

Nothing here modifies the matcher, `matching_v5`, or the first rater's labels.
No candidate V6 policy is implemented anywhere in it.

```
RUBRIC.md               what the second rater reads first
packet.md               the blind packet: 47 requirements, 17 pairings   <- GENERATED
answers_template.json   copy to answers.json and fill in                 <- GENERATED
manifest.json           row id -> case/requirement. ANALYST ONLY         <- GENERATED
build_packet.py         regenerates the three files above from both datasets
analyze.py              run after answers.json exists
```

The packet draws on **two** datasets, and the difference between them decides
what every number in the report is allowed to mean:

| rows | from | has a first rating? | can enter an agreement statistic? |
|---|---|---|---|
| R01-R27 | `declared_only_v1` | yes — the AI first rater | yes |
| R28-R47 | `declared_only_v2` | **no** — fixtures only | **no** |

The second rater is not told which is which, and should not be.

## The audit trail

The first rating is untouched and stays that way. `ground_truth.json` is
byte-identical to the file frozen before the original matcher run:

```
sha256(../ground_truth.json) = 0f96c6d6374ca781ff4372f67329ec9c83af4b3af4175edfa23abcb2786b1f04
```

The second rating lands in `answers.json` in this directory and is never merged
into the dataset. `analyze.py` reads both and joins them on `row_id`, so each
reading remains separately readable, separately attributable, and separately
revisable afterwards. If a third rater is ever added, they get `review_r3/` and
the same treatment.

## What is in the packet, and why it is 47 rows and not 14

The mandated set is the **14 contested declared-only judgments**. The packet
also contains the **13 declared-only judgments the first rater did not flag**,
unmarked and interleaved, as blind controls — and, since M1, the **20
`declared_only_v2` rows**, which cover the evidence shapes §G of the analysis
says are missing and which no rater has seen at all.

This is not scope creep; without them the exercise cannot be interpreted. An
inter-rater agreement figure computed only over rows already known to be hard
has nothing to be compared against — if two raters agree on 60% of the contested
rows, that is alarming if they agree on 100% of the easy ones and unremarkable
if they agree on 65% of everything. `analyze.py` reports the two strata
separately for exactly this reason, and criterion C1 makes the control rows a
precondition for reading anything else.

The rater is not told which rows are which. `manifest.json` records it, and the
rubric asks the rater not to open that file until they have submitted.

## How the packet is kept blind

`packet.md` is generated by `build_packet.py` from an **allowlist** of fields,
never a denylist, and the generator refuses to write a packet that contains any
of the following (`_check_no_leaks`):

- the first rater's verdicts, rationales, contested flags or contested notes;
- the matcher's verdict, evidence tier, confidence or any benchmark score;
- any candidate policy, or any hint that policies are being compared;
- the `aspect` labels, which name the failure mode a row was authored to probe;
- the fixture `label`, `summary` and `note` fields. In this dataset those are
  authoring metadata that say outright what each fixture was built to test
  ("three wholly uncorroborated claims", "the decisive pairing"), and they would
  hand the rater the answer;
- internal ids — `d_senior_bare`, `c10_senior_bare_x_platform`, `s_k8s` — which
  leak the same thing in a shorter form. Candidates are relabelled A-F and
  pairings 1-10.

What the rater does get is each profile **in full**. Showing only the items
relevant to a requirement would pre-select the evidence and bias the reading
toward MATCHED; the rater sees everything the profile records and decides for
themselves what is relevant, which is what a hiring reviewer does.

To regenerate after any dataset change:

```
python evaluation/datasets/declared_only_v1/review_r2/build_packet.py
```

## What the rubric does and does not supply

The rubric fixes the three verdict definitions and six ground rules that are not
under test (judge from the documents, judge as of the date, nothing anywhere is
MISSING, a computable shortfall is MISSING, overlapping roles count once, read
the quoted line).

It deliberately **withholds** `matching_real_v1`'s reviewer rules 1, 2, 6 and 7 —
the ones that say what an uncorroborated claim, a project technology or a stated
number of years is worth. Those rules are the thing being evaluated. Handing
them to the second rater would measure whether a person can apply a rule, which
is not in doubt, and would make the result circular.

**This is a real methodological cost and should be stated whenever the numbers
are quoted:** the two raters are not applying an identical instruction set, so
strict inter-rater agreement understates their consistency on everything except
the question at issue. That is the trade that was made, on purpose. The control
rows are what keeps it honest — they are rows where the withheld rules were not
load-bearing for the first rater either.

M1 added four codes and changed nothing else about the rubric. `S0`-`S3` and
`D0`-`D3` are byte-identical to what they were, because the 27 original rows
were classified against them; the additions cover shapes those codes genuinely
cannot express, which the v2 fixtures introduce:

- `S4` / `S5` — described in a project / in a paid role, and declared nowhere.
  The reverse of everything the tier model was built around.
- `S6` — declared, and contradicted by a description elsewhere in the profile.
- `D4` — the posting asks only for exposure, familiarity or awareness, a bar
  *below* ordinary use. Distinguishing `D4` from `D0` is what makes the review
  able to say anything about the exposure-wording policy option at all; without
  it, "Kubernetes" and "Familiarity with Kubernetes" would be recorded as the
  same kind of ask.

The rater also records two descriptive classifications per row, which are the
actual scientific payload: what shape the profile evidence takes (`S0`-`S6`) and
what the posting's words demand (`D0`-`D4`). Section 3 of the analysis crosses
them, which is what says what a human *does* with each situation a policy would
encode — as opposed to which policy happens to score best.

### The S3 tripwire

Every row in this packet is one the engine graded `declared_only`, meaning no
paid role's description demonstrates the token. If the second rater marks a row
`S3` — declaration corroborated by employment evidence — then either they
misread the profile, or **the matcher failed to attribute a role description to
the technology it names**, which is a live defect class in this codebase
(`docs/matching-v5-architecture-analysis.md`, §C). `analyze.py` prints those
rows under a tripwire banner and says to read them before anything else.

Similarly, an `S2` classification marks a row where the rater saw a project
description corroborating the claim. The engine cannot see that distinction at
all: a project description's mention is suppressed when the same project already
declared the technology (`profile_index.py:318-322`). Any `S2` row is therefore
evidence about a representation gap, not just about a verdict.

## Running the analysis

```
python analyze.py --validate     # is answers.json complete and well-formed?
python analyze.py                # the report
```

Until `answers.json` exists, `analyze.py` prints what is missing and exits 1. It
computes six sections: inter-rater agreement with Cohen's kappa over both
strata; every disagreement with both rationales side by side; the shape/demand
cross-tabulation; false-match counts for the **current, unchanged** policy
against each rater and against the rows they agree on; each candidate policy
scored counterfactually; and a sufficiency check.

**The script never selects a policy, and neither should the report it prints.**
Its five criteria were written before any second rating existed:

| | what it asks |
|---|---|
| C1 | do the raters agree on the control rows? (raw ≥ 0.85, kappa ≥ 0.60) |
| C2 | do ≥ 70% of the contested rows resolve to the same verdict? |
| C3 | does the leading policy's margin exceed the number of rows left unresolved? |
| C4 | is the leading policy's false-match count no worse than the status quo's? |
| C5 | are there ≥ 30 observations both raters agree on? |

**C5 still cannot be met, and adding rows did not change that.** C5 counts
observations *both raters agree on*. `declared_only_v1` holds 27 rows with a
first rating, so 27 remains the ceiling however long the packet gets. The 20
`declared_only_v2` rows have one rater by design — a model may not author the
other — so they raise the number of human-rated observations from 27 to 47 and
leave the agreement count exactly where it was.

That is not a gap in the package; it is the honest shape of the problem. Three
ways out, none of which this package may take on its own:

1. **A second human on the v2 rows.** Two humans rating them makes them agreed
   observations, and C5 becomes reachable at 47.
2. **Re-scope C5 explicitly**, to count human-rated rather than mutually-agreed
   observations, recording who decided and why. A pre-registered criterion may
   be changed; it may not be changed quietly, or by the party whose result
   improves when it changes.
3. **Accept that C5 fails** and treat the whole exercise as description rather
   than decision support, which is what `analyze.py` prints when it fails.

`analyze.py` reports the human-rated count beside the agreed count, explicitly
labelled as not a criterion, so the two can never be confused in a summary.

If every criterion is met, the correct next step is still a decision meeting,
not a merge.
