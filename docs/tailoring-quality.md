# Tailoring quality

Why a tailored resume that passed every grounding check was still not worth
sending, and what "useful" was defined to mean so it could be measured.

The companion to `docs/resume-tailoring.md`, which describes what stops the
document saying something false. This one describes what stops it being
useless — a separate obligation, neither ranked above the other, and the one
that had no measurement behind it.

---

## The document that started it

One real profile (`resume_profile_v1`, read by the real resume pipeline) against
one real posting (`j_backend_senior` from `matching_real_v1`: a Senior Backend
Engineer role wanting Python, Django, PostgreSQL and Docker).

Grounding: **passed, 0 errors, 0 warnings.** The rendered DOCX:

```
Senior Backend Engineer
Prepared for Senior Backend Engineer
SUMMARY
• Rebuilt the shipment tracking service in Python and FastAPI, cutting p99 latency by 63%…
• Introduced Kafka-based event streaming, replacing a nightly batch job…
• Reduced infrastructure spend by 31% by right-sizing ECS services.
SKILLS
Relevant to this role: AWS, Django, Docker, Kubernetes, PostgreSQL, Python, Redis
Backend: Celery, FastAPI, REST APIs, gRPC
Cloud & Tooling: GitHub Actions, Load Testing, Terraform
Data: Kafka, Query Optimisation, dbt
Languages: Go, SQL, TypeScript
EXPERIENCE
Senior Backend Engineer, Northwind Logistics          Mar 2022 – Present
• Rebuilt the shipment tracking service in Python and FastAPI, cutting p99 latency by 63%…
• Introduced Kafka-based event streaming, replacing a nightly batch job…
• Mentored 4 engineers through design review and on-call onboarding.
Backend Engineer, Cavendish Health                    Jul 2019 – Feb 2022
• Reduced infrastructure spend by 31% by right-sizing ECS services.
• Built HL7 and FHIR ingestion pipelines processing 250k patient records daily…
PROJECTS …  EDUCATION  University of Bristol — BSc, Computer Science  (Jan 2015 – Jan 2018)
CERTIFICATIONS  AWS Certified Solutions Architect — Amazon Web Services  (Jan 2023)
Generated by EasyApply from a confirmed profile version. Every statement above is
drawn from the candidate's own recorded career data.
```

The candidate's name is **ALEX MORGAN**. It appears nowhere. Neither does their
email, phone, location, LinkedIn, GitHub or portfolio — all six of which are on
the profile version being tailored.

Three of the eight content lines are printed twice. The education dates say
January; the resume said "2015 - 2018". The last line is a vendor watermark on a
document sent to an employer under someone else's name.

It is worth being precise about what this is. Nothing above is false. It is the
wrong true content, in the wrong order, on a page with nobody's name on it — and
no grounding check in the world objects to any of that, because none of them is
a claim the profile does not support.

## Root cause

Four defects, one of which caused four of the others.

### The ranking signal was 75% noise

Every selection decision — which clause leads a job, which project survives,
which skills are "relevant", which requirements the document claims to target —
came from one number: how many of the posting's words a piece of text reused.
That vocabulary was built by pouring every requirement into one set. For
`j_backend_senior` it held 37 terms, of which **9 carried skill signal**:

```
ACTUAL SIGNAL  python django postgresql docker kubernetes redis aws 3+ 5+
STOPWORDS      be in must of or the to with within
ELIGIBILITY    authorised based berlin cet eu hours legally two work
FILLER         building certified developer engineering experience
               production professional services software years
```

The consequences were not subtle, and each was traced to the exact token:

| Outcome | Caused by |
|---|---|
| A Kafka bullet ranked 2nd in the whole profile | `hours`, `to` — "18 hours" scoring against *"within two hours of CET"*, a commute policy |
| A cost-cutting line outranked the flagship HL7/FHIR pipeline bullet | `services` |
| The Python/FastAPI bullet led — correctly, but by luck | scored 3, of which 2 were `in` and `the` |
| The document claimed to target *"3+ years … with Django"* while containing no Django | `services`, `with` |
| It claimed *"Must be legally authorised to work in the EU"* | `in`, `the`, `to` |
| It claimed *"Based in Berlin, or within two hours of CET"* for a candidate in Bristol | `hours`, `in` |
| It did **not** claim Docker, Kubernetes or Redis, all of which it evidences | `_targeted` never looked at the skills section or the certifications |

Classification: **context-selection** (what enters the ranking) and
**relevance-selection** (how it is ranked).

### The schema could not carry a resume

`TailoredResumeDocument` had no contact fields, by an explicit decision recorded
in its own docstring: *"the only reliable defence against a field being filled in
is for the field not to exist"*.

That reasoning is correct about `years_of_experience` and wrong about a name,
and the distinction it missed is **checkability**. `years_of_experience` is
dangerous because no column holds it — whatever a generator writes there, the
validator has nothing to compare against. `full_name`, `email`, `phone` and
`location` are columns on the profile version, read off the user's own resume.
They can be compared exactly, by the same check that catches a promoted job
title.

Leaving them out prevented no fabrication. It produced a resume an employer
could not reply to.

The same schema dropped education date precision, which is why the renderer
printed "Jan 2015" for a resume that said "2015" — a false fact introduced
*after* grounding had finished looking.

Classification: **schema/model limitation**.

### The summary was the bullets again

`_summary` selected the three highest-scoring clauses in the profile. Those were,
predictably, three of the bullets printed immediately below it. Meanwhile the
version's own `summary` column — the paragraph the candidate wrote about
themselves, quotable verbatim and already summary-shaped — was never read.

It could not have been read, as it happens: `grounding._snapshot_field` walked
the child rows looking for a column called `summary`, and the summary lives on
the version. A document quoting it would have been rejected.

Classification: **generation**, with a latent **grounding** gap behind it.

### The renderer printed our plumbing

`Prepared for <job title> at <company>` at the top and `Generated by EasyApply…`
at the bottom. The first tells an employer that a machine aimed this document at
their vacancy; the second is a vendor watermark on the candidate's resume. The
renderer also hardcoded `"month"` precision for education and certification
dates.

Classification: **rendering**.

## What changed

### A separate module for selection

`app/services/tailoring/relevance.py` is new, and the split is the point: the
question "which true sentences speak to this job" now has one owner, one set of
tests, and no ability to affect what may be *said*. Grounding does not import it
and never consults it.

Requirements keep their kind and their weight rather than dissolving into a bag
of words:

- **Named things** (skills, technologies, certifications) are never stopworded —
  "Go" is a two-letter word and a required language — and are weighted highest.
- **Free text** contributes only its distinctive words. Stopwords go, and so does
  the filler every posting and every resume share.
- **Eligibility requirements score nothing.** A visa and a commute are real
  requirements and no achievement on a resume is evidence of either.

And what a document may claim to have *targeted* is decided per requirement, in
the place that kind of requirement can actually be answered:

- a **named** requirement needs its **whole name** — "AWS Certified Developer"
  and "AWS Certified Solutions Architect" share two words of three, and any-word
  matching claims the first credential from someone holding only the second;
- an **experience** requirement is answered by **prose only**. A skills line
  reading "Django" does not evidence three years of Django employment — while
  the *skill* requirement "Django" from the same posting is answered by that
  line, honestly and separately.

### Four smaller changes, each at its own layer

| Layer | Change |
|---|---|
| schema | `TailoredContact` + `TailoredLink`; date precision on `TailoredEducation` |
| grounding | `_check_contact` (exact, same strictness as a company name); links checked against the version's own rows; education precision checked as a copied field; the version's `summary` became a valid haystack |
| generation | the candidate's own summary is used verbatim; bullets never duplicate it; skills ordered by the posting and the tail capped; an irrelevant job keeps fewer bullets |
| rendering | a real contact header; no "Prepared for"; no footer; precision honoured; the summary as a paragraph rather than a bullet |

`render()` no longer takes the job title or the company. The posting reaches the
renderer through the document or not at all.

### Selection moves when the posting moves

The same profile against `j_platform_k8s` (Kubernetes, Terraform, Go; both
certifications):

```
Relevant to this role: Kubernetes, Terraform, Go, AWS
PROJECTS  Observability Starter Kit — Terraform, Grafana, Prometheus
```

The Observability project scored **zero** under token overlap and was dropped
from every document. It is now the lead project for the posting it answers, and
the Ledger project — right for the backend role — is correctly absent.

Against `j_sre_health`, which asks for on-call participation and healthcare
domain experience, the two bullets that token overlap scored at zero are now the
two that lead their entries.

## How it is measured

`evaluation/datasets/tailoring_v1/` — one profile, four postings, chosen so the
candidate stands in a different relation to each. Expectations were authored from
the resume and the postings **before** the generator was changed and are not
edited to match an output.

Every expectation is a property a machine can check. There is no human quality
score, because a judgement nobody can re-run is not a regression test.

The load-bearing case is `frontend_react`: a backend engineer against React,
JavaScript and Jest, none of which is anywhere in the profile. An engine that
looks good on a strong match and reaches on a weak one is an engine that will
eventually put a word on a resume the user has to defend in a room. The assertion
is the blunt one — those strings do not appear in the document or the rendered
DOCX, in any section, at any position.

Two of the four cases caught real bugs in the new code before it shipped: `with`
was missing from the stopword list beside `within` and `without`, and named
requirements were matching on any word rather than the whole name. Both were
found by expectations written before the code existed.

## Hardening free-text evidence

A later review found the first version of the rule above too permissive: a
free-text requirement was answered by ONE of its distinctive words, which let
`j_platform_k8s` claim

    "Experience in regulated financial services"

for a candidate who has worked in logistics and healthcare, on the strength of
`regulated` in their summary ("...across two regulated industries").

What made it hard is the requirement it sits beside. The same token, from the
same sentence, is the only support for

    "Experience in healthcare or another regulated domain"   (j_sre_health)

and that claim is **correct** — the posting accepts any other regulated domain,
and theirs is one. An audit of every free-text claim in the dataset found all of
them resting on exactly one matched token:

| Requirement | matched | verdict |
|---|---|---|
| Experience in regulated financial services | `regulated` (1 of 2) | wrong |
| 6+ years of professional infrastructure experience | `infrastructure` (1 of 2) | over-claims |
| Experience in healthcare or another regulated domain | `regulated` (1 of 4) | right |
| Participation in an on-call rotation | `on-call` (1 of 3) | right |

So no threshold on count separates them, and **proportion ranks them backwards**
— the wrong claims match half their words, the right ones a quarter and a third.
The difference is not how much matched. It is what the requirement will accept:

- **"or" means alternatives.** `_alternatives` splits a free-text label on `or`
  and requires one alternative COMPLETELY. "another regulated domain" is an
  acceptable answer in its own right and is fully covered by `regulated`;
  "regulated financial services" offers no alternatives and needs both words.
- **A term of art carries its alternative alone.** A token with internal
  punctuation — `on-call`, `ci/cd`, `front-ends` — is a named practice rather
  than an English word, the same observation grounding's proper-noun check rests
  on. Where an alternative contains one, that is what must match.
- **Bare quantities are dropped.** No sentence evidences a duration by
  containing the characters `5+`, and requiring it would make every requirement
  stating a number permanently unanswerable — a different wrong answer, not a
  stricter one.

Education keeps the permissive rule deliberately: it is checked against the
education section alone — institution, degree and field, all transcribed — so
two words landing there is not the coincidence that two words landing anywhere
in a page of prose is. Named skills, technologies and certifications are
untouched, still requiring their whole name.

The change can only ever REMOVE a claim, and that is asserted rather than argued
(`test_tightening_can_only_ever_remove_a_claim` probes every single-token
evidence set and every vocabulary prefix, checking the new verdict is a subset of
the old). Grounding is unchanged and still never consults this module.

## Remaining limitations

- **A free-text requirement whose whole distinctive content is one word is
  still claimed from that word.** `j_platform_k8s` asks for *"6+ years of
  professional infrastructure experience"*; once the duration is set aside the
  requirement is "infrastructure", the document says "infrastructure", and it is
  claimed. That is full coverage of what the requirement distinctively asks
  rather than one word out of several — but it is not evidence of six years, and
  a requirement stating a duration is one this domain cannot fully judge.
  `minimum_years` is matching's to evaluate, not tailoring's.
- **The generic-noun list is the weakest link in the free-text rule.** Reading
  "another regulated domain" as fully answered by "regulated" depends on
  `domain`, `area`, `sector`, `industry` and their neighbours being treated as
  container nouns that never identify anything. That list is hand-written, and a
  posting using one of those words substantively would be read too loosely. It
  errs in the direction of claiming slightly more, never of saying something
  false: a wrong entry here mis-states what the document aimed at and can never
  put a claim about the candidate on the page.
- **Contact links are deduplicated by label and capped at four.** A profile
  version stores personal and project links in one list with no way to tell them
  apart, so a project's "Demo" link can reach the header. Distinguishing them
  needs a column on `ProfileLink`.
- **Certification dates print the year only.** `Certification` has no precision
  column, so a stored `2023-01-01` may be "January 2023" or a resume that said
  "2023". Printing the month would invent that distinction about half the time.
  Adding the column upstream would let a certification dated to a month say so.
- **The stopword and eligibility lists are English and hand-written.** They err
  towards dropping signal rather than admitting noise, and neither can affect
  what a document may *say* — only what it leads with.
- **The AI generator is still unmeasured and still off.** None of the defects
  above needed a model, and that remains the finding. What has changed since is
  that it can now be measured — `evaluation/tailoring_runner.py` scores a model
  against this same dataset, and the deterministic generator scores 1.0 on every
  measure, which is what makes any number it reports about a model meaningful.
  See `docs/llm-tailoring.md`.
